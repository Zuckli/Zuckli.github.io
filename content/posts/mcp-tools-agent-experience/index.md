在近期一次 Agent 系统的工具调用审计中，我遇到了一个值得反复讨论的问题：系统已经提供了发现、读取、创建、更新、关联和核对等完整能力，Agent 仍然需要经过大量试探，才能完成一次看似简单的业务修改。

这套系统管理的是交付物。人工预先配置对象模板、属性、文件槽位和对象之间的关系，再由具备权限的 Agent 根据 Skill 和用户要求维护内容。这样的分工有明确价值：业务结构可以稳定保存，内容可以持续演进，权限和版本也有服务端保障。

实际调用却暴露出不少摩擦。Agent 已经读过内容，提交时仍被要求补读；对象创建成功，还要再次读取才能获得可填写的属性入口；一次修改涉及几个相关字段，需要拆成多次调用；工具返回成功，最终答复却没有区分正式保存、候选待确认和内容尚未完成。

最初的优化思路集中在参数说明、分页、错误提示和返回内容上。这些都需要改。但沿着调用链继续追踪，会发现另一些问题来自职责分配：系统把内部状态管理交给了模型，而模型为了完成业务任务，不得不先理解一套额外的操作流程。

这篇文章记录的是这次审计形成的设计判断。具体业务和工具名称并不重要，更值得保留的是：当一个系统通过 MCP 向 Agent 开放持久状态时，怎样安排判断、执行和验证的边界。

## 一、业务模型需要进一步转化为操作模型

传统业务系统往往先建立领域模型，再围绕资源提供 API。对象、属性、关系、目标、批次和维护记录，都可以拥有各自的查询和修改接口。这种组织方式方便程序调用，也便于表达领域约束。

把这些接口直接整理成工具，并不能自然得到一个适合 Agent 使用的系统。

程序员可以阅读完整文档，把调用顺序固定在代码里。Agent 则需要在执行过程中决定下一步：当前拿到的是类型还是实例，应该先创建对象还是选择关联，哪个版本用于编辑，哪个标识用于核对，保存之后是否还需要额外操作。

每一个没有显式表达的前置条件，都会成为一次推断。每一个缺少恢复入口的错误，都会增加下一次试探。

因此，工具设计需要增加一层操作模型：围绕用户意图，把完成动作所需的目标、约束、依据和结果组织起来。例如，“创建一份记录并填写初值”应当有明确的操作边界；“修改同一对象中相关的几个字段”也应该能够表达为一个业务变更，而不是要求模型自行拼装若干内部步骤。

操作边界必须与实际能力一致。如果后端只能分别提交这些步骤，工具就需要明确说明部分成功的可能性。只有底层确实保证同一事务，才可以承诺原子提交。

工具数量也不能单独作为设计指标。把几十种动作放进一个通用管理工具，虽然减少了名称，却可能扩大参数空间和选择难度。一个工具是否合适，取决于它的职责是否清楚、前置条件是否可获得、结果是否足以支持下一步。

审计时，可以先选择一条具体任务，逐次观察 Agent 为何调用每个工具。用于业务判断的调用通常有必要；仅为取得上一步本应返回的身份、版本或状态而增加的调用，往往说明操作模型还不完整。

## 二、系统应承担确定性的工作

Agent 的价值主要体现在存在语义和业务歧义的地方，例如解释需求、选择适用对象、生成内容，以及判断上游变化是否要求下游调整。

授权、版本比较、格式校验、唯一关联匹配、影响计算和审计，则应由系统负责。把这些工作交给模型逐项操作，会同时增加成本和不确定性。

一个常见例子是关系绑定。如果模板和实例范围已经确定，并且只有一个合法目标，系统可以按照既有规则完成绑定。出现多个合法候选时，再让 Agent 根据业务意图选择。这样的划分既保留了判断能力，也避免了让模型重复执行确定性规则。

相同原则也适用于变更后的维护流程。系统能够计算哪些对象受到影响、哪些证据已经过期，以及哪些事项需要人工决定。Agent 应当获得这些事实，并对确实需要理解内容的部分作出判断。为了让内部状态进入“完成”，要求模型反复登记批次、更新标记或复制版本信息，会使业务任务依赖不必要的记账流程。

系统提供操作依据时，还要考虑业务结构的动态性。通用工具的静态参数说明，无法完整覆盖不同对象的字段类型、基数、枚举和文件要求。目标的实际定义应当能够按需读取，并与准确版本绑定。

例如，修改一个结构化属性时，Agent 需要获得合法值的约束；维护一份文件型方案时，它需要获得文件身份、版本和写入入口。空属性列表不能被解释为没有正文，显示名称也不能替代真实资源身份。

这里还涉及三种容易混淆的信息：

| 信息 | 能够说明什么 |
| --- | --- |
| 负责角色 | 谁通常承担这项工作，出现问题时可以向谁协调 |
| 有效权限 | 当前主体是否获准执行本次操作 |
| 工具可用性 | 当前会话是否拥有可以完成操作的入口 |

三者可能同时成立，也可能只成立其中一部分。工具结果需要让 Agent 看见这种区别，服务端则必须在实际执行时重新校验权限。

Skill 可以解释业务方法，Prompt 可以表达本次意图。身份、作用域和授权仍应来自可信的运行上下文。

## 三、读取、保存和完成需要各自的证据

“先读再写”是一种常见保护思路，但读取记录只能证明系统交付了某些内容，无法证明模型已经理解，更无法证明修改满足了业务约束。

如果读取结果经过分页、截断或运行时裁剪，甚至连“交付了哪些内容”都需要仔细界定。服务端生成了完整响应，和模型最终获得了完整正文，是两个不同事实。

可靠的读取结果应该说明：当前内容的版本、实际返回的范围、是否还有未返回部分，以及可直接使用的续读入口。搜索命中也应提供可追溯的原文和位置，并说明哪些内容没有进入本次检索。未扫描的文件不能被解释为没有匹配。

这些信息用于帮助 Agent 获取证据。写入时是否安全，还需要由目标版本、实际输入依据和业务规则共同判断。模型自行声称“已经读过”，不能代替服务端校验；要求全文送达，也不能代替语义判断。

保存结果存在类似问题。一个简单的 `success` 往往承担了过多含义。

| 状态 | 实际回答的问题 |
| --- | --- |
| 提交成功 | 本次操作是否被可靠地接受并提交 |
| 正式生效 | 哪些内容已经成为当前正式状态 |
| 等待确认 | 哪些变更仍需要用户决定 |
| 内容完整 | 是否满足明确配置的交付条件 |
| 关联一致 | 相关变化是否按规则完成处理 |
| 用户任务完成 | 本轮承诺的结果是否实际交付 |

例如，某类系统允许文件立即保存，同时为业务对象生成待确认候选。此时，“文件已保存”和“业务候选待处理”都是真实结果。用一个总状态覆盖它们，会影响 Agent 的后续操作，也会误导最终汇报。

同样，一份空记录没有维护待办，并不能证明它已经满足用户要求。系统应当返回自己能够证明的状态和适用范围；没有配置完整性条件时，就明确说明缺少判断依据。

这类状态设计不只是展示问题。Agent 会根据返回结果决定继续修改、等待用户、重新读取还是结束任务。模糊的状态会把错误传播到后面的每一个决定。

## 四、失败恢复应在第一版协议中设计

持久写入最难处理的情况之一，是请求超时后无法知道操作是否已经完成。

假设 Agent 创建一份记录，数据库已经提交，但返回结果在网络中丢失。直接重试可能产生重复记录；直接结束又可能把真实成功报告为失败。仅有一个“可重试”的错误字段，无法解决这个问题。

工具需要稳定的操作身份，并将它与原请求、实际执行和持久收据关联起来。同一次操作的重试应当恢复原结果；用户明确提出的另一项操作，即使内容相同，也应有表达独立意图的方式。

参数摘要可以辅助识别重复请求，但它无法独自区分“重试一次创建”和“再次创建同样内容”。宿主生成新的操作标识后，还必须让底层使用与之对应的独立幂等键，否则新的标识只是一层展示。

版本冲突则需要另一种处理方式。它说明原操作所依据的事实已经变化，应当读取差异并重新判断。适配器若自动获取最新版本，再提交原内容，可能把原本可见的冲突变成静默覆盖。

因此，至少应明确区分参数无效、业务条件不满足、权限拒绝、版本冲突、暂时故障和结果未知。每一类都需要可执行的恢复路径。错误说明的目标，是帮助 Agent 判断下一步，而不是让它对同一个请求持续尝试。

恢复设计还必须与内部执行链路一起检查。读取工具如果同时扫描大量历史、写入交付记录或取得大范围锁，扩大单次返回量未必能解决延迟。需要测量数据库等待、内容加载、关系计算、序列化和运行时投影，确认时间实际花在什么地方。

日志也应从工具请求进入时开始记录。参数校验阶段失败的调用可能根本到不了业务服务；只看业务审计，就会漏掉一部分最影响 Agent 体验的问题。

## 五、兼容性约束需要保护到实际语义

这类改造通常发生在已经被其他客户端使用的系统中。Agent 工具希望提供更适合模型的输入和结果，管理后台、人工操作和其他服务却仍然依赖原有接口。

一个可行的边界是：新 Agent 交互层组织操作和解释结果，底层继续执行原有授权与领域约束。新旧调用方可以获得不同粒度的视图，但它们看到的业务事实必须能够对应。

兼容性检查需要覆盖字段、默认值、枚举、错误码、版本、事件和幂等行为。对于严格解析结果的客户端，增加可选字段也可能造成失败；新结果格式应当经过明确协商，不能默认替换旧格式。

旧会话和新旧服务并存时，这个要求尤其重要。工具发现显示支持某个参数，后续调用却命中不支持它的旧实例，不能依靠静默忽略字段来维持“成功”。如果被忽略的是原子性或处理范围，实际效果就可能已经偏离用户意图。

另一方面，兼容也不要求保留低效的内部实现。查询、缓存、事务和锁都可以重构，只要旧消费者的有效合同得到保持，并通过回归验证。已知缺陷与既有协议之间的边界，需要明确分析，不能把两者一起冻结。

有些问题确实涉及业务规则。例如，对象级关系要求任意内容变化后都重新核对下游，那么交互优化可以减少重复查询和展示，却不能自行删除这些义务。需要缩小影响范围时，应作为独立的业务配置变更评审。

这样才能说明一项改造究竟消除了什么：是减少了模型的推断，改善了执行效率，还是改变了业务要求。三者的验收依据并不相同。

## 六、用完整任务验证工具设计

审计中最容易误用的指标，是调用次数和错误率。

调用减少，可能来自更完整的操作，也可能来自少读了必要内容。错误率下降，可能来自契约修复，也可能来自把拒绝包装成成功。一次权限拒绝或版本冲突，反而可能说明保护机制正常工作。

我更倾向于从一项完整任务验证设计。例如，“修改一条业务规则，并同步相关测试”。观察它是否定位了准确内容、读取了必要依据、保存了预期变化、处理了真实影响，并向用户说明仍然存在的待确认或未完成事项。

随后再比较工具往返、重复内容、总耗时、人工介入和失败恢复。还需要主动制造几种情况：写入成功后丢失响应、执行期间来源变化、角色权限被撤销，以及新旧服务同时处理请求。

这些检查能够暴露单工具测试很难发现的问题：每个接口都返回了正确结果，组合以后却缺少操作身份；每一页内容都完整，运行时聚合后却丢掉了后半段；保存和核对分别成功，最终答复仍把待确认内容说成正式交付。

对这轮审计，我能确认的是设计上应该消除哪些不必要的负担，不能据此宣称改造已经降低了多少成本。收益需要在相同任务、权限和数据条件下实测，失败案例也应保留在结果里。

以后评审 MCP 工具，我会先要求展示一条完整任务的调用轨迹：每一步需要作出什么判断，判断依据从哪里来，实际改变了什么，中断后怎样继续。若其中某一步只是在搬运系统早已知道的信息，就应当先检查这一步为什么还需要模型参与。
